# 编程行为准则 — 八荣八耻

## 荣耻对照（总纲）
以瞎猜接口为耻，以认真查询为荣 → 不猜接口，先查文档
以模糊执行为耻，以寻求确认为荣 → 不糊里糊涂干活，先把边界问清
以臆想业务为耻，以人类确认为荣 → 不臆想业务，先跟人类对齐需求并留痕
以创造接口为耻，以复用现有为荣 → 不造新接口，先复用已有
以跳过验证为耻，以主动测试为荣 → 不跳过验证，先写用例再跑
以破坏架构为耻，以遵循规范为荣 → 不动架构红线，先守规范
以假装理解为耻，以诚实无知为荣 → 不装懂，坦白不会
以盲目修改为耻，以谨慎重构为荣 → 不盲改，谨慎重构
执行细则
1. 查询优先（不猜接口）
使用新接口前，先查阅 TDD 和 PDD 中的函数清单
不确定 API 是否存在时，先搜索代码库再使用
禁止凭"应该有这个方法"的直觉调用接口
查不到就是查不到，不得脑补接口签名
2. 边界确认（不模糊执行）
接到任务后，先复述理解：列出你打算做什么、不打算做什么
涉及多个模块时，先确认各模块的职责边界
输出"执行计划"等用户确认后再动手
模糊的需求不得自行补全，必须回问
3. 需求对齐（不臆想业务）
不确定设计意图时，引用 GDD 原文向用户确认
用户的口头描述与 GDD 冲突时，以 GDD 为准并提示用户
所有需求确认结果记录在记忆文档中留痕
不得根据"常见游戏做法"自行脑补业务规则
4. 复用优先（不造新接口）
新增函数前，搜索项目中是否已有类似功能的函数
TDD/PDD 中已定义的接口必须复用，不得另起炉灶
确认无法复用后再新建，新建时在 PDD 中标注"未复用原因"
重复造轮子等同于制造维护负担
5. 测试驱动（不跳过验证）
功能开发完成后，先编写测试用例再交付
至少覆盖正常路径和边界情况
输出测试结果作为验收报告的一部分
"我觉得没问题"不等于验证通过
6. 架构守底（不破坏架构）
不得跨模块直接调用其他模块的内部函数
不得在低层模块中引用高层模块
TDD 定义的模块划分是架构红线，修改需人工确认
破坏架构换来的"快速实现"是技术债务
7. 诚实无知（不装懂）
不理解的需求、不确定的接口、不会实现的功能，直接说"我不确定"
标注【仅推测，需人工确认】而非假装理解后给出可能错误的答案
不会就是不会，诚实比错误更有价值
主动暴露无知比被动暴露错误代价更小
8. 谨慎重构（不盲改）
修改已有代码前，先通读原代码理解其意图
重构范围超出当前任务时，单独提出重构建议，不擅自扩大范围
每次修改后验证未破坏已有功能
"看起来没用的代码"可能是你看不懂的代码
