## 1. Demo 简介

### 是什么

「卡牌冒险者」是一款融合 **D&D 5e规则 × 魔法船(Spelljammer)太空奇幻世界观** 的回合制卡牌RPG游戏。采用**纯HTML/CSS/JavaScript单文件实现**,无需服务器,浏览器双击即玩。

它不是一个"完整游戏",而是一个**经过系统化设计、可以跑通核心战斗循环的可交互原型**——有完整的回合制战斗、3×3网格走位、CSV数据驱动等核心玩法。

### 面向谁

- 喜欢《杀戮尖塔》《命运之手》等卡牌Roguelike的策略玩家
- 对D&D深度角色构建感兴趣的桌游爱好者
- 想体验"太空奇幻"题材(Spelljammer魔法船)的RPG玩家

### 主要功能

**功能1:三层玩法架构**

游戏设计了L1→L2→L3三层递进结构:
- **L1 地图层**:星域探索·区域选择·路径规划,消耗AP(行动力)进行宏观决策
- **L2 网格层**:5×5网格翻牌事件,战斗/商店/篝火/宝箱随机分布,消耗EP(探索点)
- **L3 战斗层**:回合制卡牌战斗,消耗CE(战斗能量)+ 职业能量,这是当前可体验的核心层

## 2. Demo 创作思路

### 灵感来源

两个问题驱使我开始这个项目:

1. **现有卡牌Roguelike的角色构建太浅了**——大多数游戏只有简单的数值成长。D&D 5e有6属性、种族/出身、技能、专长、传奇道途这些深度的角色构建层次,为什么不把它们融入卡牌战斗?

2. **Space is cool, but no one made a spelljammer card game yet**——魔法船(Spelljammer)是D&D设定里最有想象力的部分:魔法驱动的星舰、星海中的冒险、星界巨兽……但市面上没有任何游戏做了这个题材。

所以「卡牌冒险者」的定位是:**D&D的深度角色构建 × 杀戮尖塔的卡牌战斗爽感 × 魔法船的太空奇幻舞台**。

### 想解决的问题

| 痛点 | 我们的方案 |
|------|-----------|
| 角色构建浅:只有数值成长 | D&D式的种族/出身/技能/专长/传奇道途深度构建 |
| 战斗维度单一:只打牌不走位 | 3×3网格战场,前排后排策略 + 太空船5岗位分工 |
| 世界观单薄:纯地牢爬行 | 魔法船太空奇幻设定,星域探索 + 星舰战斗 |

### 为什么做这个方向

- **差异化**:市面上没有D&D规则 + 魔法船世界观 + 卡牌战斗 + 双战场系统的组合
- **技术可控**:HTML单文件实现,聚焦核心战斗循环,适合两周内的原型验证
- **展示值**:复杂的GDD文档体系 + 多Agent协作流程,能充分展示TRAE在复杂项目中的AI开发能力

### 4.2 核心技术实践:防幻觉体系演进(7步)

这是整个项目中迭代最多、踩坑最深、最终收获最大的一条线。以下按时间顺序回顾每一步:

**第1步:发现AI在编造内容** — 让AI"写几个卡牌",它编了"火球术""冰霜箭""暗影打击",全是不存在的名字。
→ 触发认知:必须有一个"什么存在什么不存在"的权威答案。

**第2步:建立ID-REGISTRY编号注册表** — 所有元素编上唯一编号,核心原则:**注册先于写入**。格式强制:`C-001`(前缀-三位补零),字母大写,不允许TBD/TEMP。

**第3步:建立防幻觉8条铁律** — 无上下文禁止编造、输出附带证据链、修改前先读原文、禁止自审、区分事实/推测、记录工具调用、冲突即时停止、输出三层分层。

**第4步:建立五步验收SOP** — PDD检查→元素清单比对→TDD-PDD一致性→数值来源验证→验收报告,不通过不得归档。

**第5步:建立残留覆盖预审(5类检测)** — 文本残留(Grep旧文本)→语义残留(Grep等价表达)→别名残留(查ID-ALIAS)→跨系统残留(查ID-REFERENCE-GRAPH)→编号一致性(比对注册状态)。

**第6步:建立三权分立写入流程** — gdd-lead/tech-lead只提案不写入,writer-agent只写入不提案,verify-lead只校验不写也不提案。写入必须经过:提案→预审→校核→确认→写入→事后校验。

**第7步:自我审计发现体系裂缝** — 用自己制定的规则审查自己的配置文件,发现4个Agent配置违反权限矩阵。

## 5. 开发心得与踩坑经历

### 心得1:AI是辅助工具,规则约束是双向的

**核心认知**:当你给AI制定规则、约束它的行为时,这些规则同样约束你自己。你不能在写入规则的时候同时违反你自己设定的规则。

**我的踩坑**:建立20条规则后,我一边要求AI"所有写入必须经过6阶段流程",一边在Agent配置文件里让gdd-lead、tech-lead等"通过MCP写入文档"。直到全项目Grep才发现了这个矛盾——4个Agent配置违反权限矩阵,writer-agent甚至没有配置文件。

**我的实践**:现在每次修改规则前先用Grep搜索全项目,确认不产生矛盾;修改后用Grep再验证。**规则是你和AI共同的契约——你先遵守,AI才会遵守。**

### 心得2:给AI一个明确的实现路径,而不是一个模糊的名字

**核心认知**:"参考杀戮尖塔的战斗系统"和"参考杀戮尖塔:每回合3能量、卡牌费用0/1/2/3、敌我分排站位、结束回合后敌人按意图行动"——**名字是模糊的,具体描述才是可执行的。**

**典型教训**:早期设计太空船战斗时我只说"参考DND魔法船设定",AI编了一套我从未听过的岗位名。后来重写为"5个岗位——星桥(导航/先攻)、燃素炉(能源/过载)、魔导炮阵(主炮攻击)、晶壁护盾(防御/护盾)、星图仪(侦查/弱点分析)"——每个岗位后面用括号锁定功能,AI立刻理解了。

### 心得3:人的边界就是AI的边界——设计主导权必须在你自己手里

**第一层:为什么不能放手让AI主导设计?** AI可以拓展你的边界,但超出你认知体系之外时,AI会给你**无法分辨真伪、无法逐项校核**的内容。更致命的是设计会**无端膨胀**——AI不断加东西,你不断点头,最后根本做不完。

**踩坑实例**:早期让AI直接设计D&D战斗规则,它给出了命中检定、豁免检定、伤害抗性的完整体系。读起来"挺好的",直到实现HTML原型才发现——在回合制卡牌里根本跑不动,计算量太大。**根因是我自己D&D认知不够深,没法校核AI的内容。**我在"黑箱"外面,只能用自然语言说"好像不太对"。

**第二层:我的三层认知闭环**:
```
GDD文档(我主导+AI辅助) → 我理解每一个设计决策
  ↓
TDD/PDD(AI生成,我校核) → 只用检查"是否符合GDD"
  ↓
CSV数据(AI填充,我校核) → 数值在我定的边界内
  ↓
HTML代码(AI实现,我验证) → 亲自玩,体验是否符合设计意图
```
核心:**AI做了80%的体力活,但我对100%的产出保有校核能力。**

**第三层:设计师的自我约束——你能删掉多少?** 不亲手写代码,就判断不了哪些是废弃残留。想删不敢删,废弃设计像杂草越长越多。现在我坚持:**有增必有减**——新增前先问"如果错了,我能干净移除吗?"不能就拒绝。

### 心得4:HTML是游戏原型的最佳载体

**核心认知**:用TRAE生成HTML实现游戏原型,ID到HTML的界面跳转、战斗模拟、回合制操控——全部非常顺畅且快。

- **回合制战斗秒级实现**:战斗顺序、属性验证、伤害计算——修改一个数值立刻在浏览器看到效果
- **特性验证即写即测**:新特性从提出到可玩经常只需几分钟
- **可视化+操作感**:设计师不再是"看文档想象",而是"亲手玩到"
- **设计师直入内容填充**:原型跑通后,在CSV里填新卡牌新敌人,刷新页面就能玩

传统开发中策划→程序→验收一个回合可能几天。TRAE+HTML后,一个下午跑通战斗原型,立刻开始填内容。**从"写文档等实现"变成了"做原型自己玩"。**

### 心得5:程序与数据分离 — CSV驱动的核心价值

调整卡牌伤害、敌人血量、技能效果,直接改CSV,无需在几千行JS里找定义。AI读CSV就能理解全部游戏数据,策划可独立修改数值。

```
data/csv/
├── _schema.csv          ← 中央注册表
├── _foreign_keys.csv    ← 跨文件外键
├── cards.csv            ← 卡牌定义
├── card_effects.csv     ← 卡牌效果
├── enemies.csv          ← 敌人属性
├── enemy_skills.csv     ← 敌人技能
└── ...(共29个CSV文件)
```
新增一张卡牌只需2个CSV各加一行,零代码修改。

### 踩坑1:AI幻觉
**解决**:ID-REGISTRY注册制 + 8条防幻觉铁律 + 5类残留检测

### 踩坑2:文档代码不同步
**解决**:6阶段写入流程 + ID变更传播4步强制约束 + .changelog.md变更日志

### 踩坑3:Agent配置矛盾
**解决**:以AGENTS.md为唯一权威源,逐行Grep全项目验证,统一20个规则文件 + 8个Agent配置文件

### 总结:几点最想说的话

1. **规则是双向的**:你写给AI的规则,你自己也要遵守。用Grep验证。
2. **描述要具体到可执行**:带着括号说明功能的名字,比"看起来很厉害"的名字有用一百倍。
3. **设计方向你定,细节AI填**:一轮一轮提问,一步一步确认。
4. **数据放CSV,代码放JS**:各改各的不打架,AI也能直接读CSV理解游戏全貌。

### 不足与反思:当前体系的6个已知限制

以下是清楚意识到但尚未解决的6个不足:

| 不足 | 说明 | 根因 |
|------|------|------|
| 1.规则靠自觉非自动化 | 20条规则全靠AI阅读理解,无Git Hook强制执行 | 规则是"文档型"而非"执行型" |
| 2.单线程AI无法真三权分立 | verify-lead审查writer-agent本质同AI自审,违反铁律4 | AI单线程,无法真正独立 |
| 3.ID格式偏差 | ID-REGISTRY用`C-001`,早期CSV用`C001` | 规则制定晚于数据创建 |
| 4.ID-ALIAS/GRAPH未补全 | 检测3/4依赖的俩文件一个空一个只覆盖4/19前缀 | 基础设施维护被延后 |
| 5.缺少自动化回归测试 | 五步验收全手动,第10次不如第1次仔细 | HTML原型阶段无测试框架 |
| 6.规则体系膨胀风险 | 20条规则/8Agent/10Skill,维护成本在上升 | 没有"规则审查规则" |

> **防幻觉是持续工程,不是一次性配置。**
