> **分析性质**:只读根因分析,未修改任何文件

## 一、核心结论

**75 个错误不是 75 个独立错误,而是 5 个系统性根因的 75 种表现形式。**

修复 75 个错误不需要 75 个补丁,而是要修复以下 5 个系统性根因:

| 根因编号 | 根因名称 | 直接导致的错误数 |
|---------|---------|----------------|
| 根因1 | 规则体系是"文档型"而非"执行型"(无自动化强制) | 约 40 个 |
| 根因2 | Agent 权限三权分立是"设计型"而非"运行型" | 约 25 个 |
| 根因3 | 规则依赖链断裂(ID-ALIAS/REFERENCE-GRAPH 失效) | 约 8 个 |
| 根因4 | 规则索引与实际规则文件脱节 | 约 2 个 |
| 根因5 | 规则与数据结构的同步机制缺失 | 约 15 个 |

> 注:部分错误由多个根因共同导致,故总和 > 75。

## 二、5 个系统性根因详解

### 根因1:规则体系是"文档型"而非"执行型"(最根本原因)

#### 1.1 现象

16 个规则文件定义了详尽的流程(6 阶段写入、5 类残留检测、5 步验收),但全部依赖 AI 手动执行,**无任何自动化强制机制**。

#### 1.2 证据

| 证据项 | 位置 | 说明 |
|--------|------|------|
| §5.3 明确标注"建议" | csv-data-management.md §5.3 | 自动化校验仅"建议",非强制 |
| 无 CI/CD 配置 | 项目根目录 | 无 .github/workflows、无 .gitlab-ci.yml |
| 无 Git Hook | .git/hooks/ | 无 pre-commit hook |
| 无校验脚本 | scripts/ | 无 Python/Node 校验脚本 |
| 校验依赖"verify-lead 手动 Grep" | write-pipeline.md 阶段3/6 | 手动校验不可靠 |

#### 1.3 后果

- 规则存在 ≠ 规则执行
- AI 在上下文压力下简化流程,跳过校验步骤
- 导致 92 个未注册 ID、版本不同步、状态机不一致等错误累积

#### 1.4 影响的错误

- P0-03(92 个 ID 未注册)
- P0-04(状态机不一致)
- P0-10(loadCSV 接口幻觉)
- P1-16~P1-21(6 处版本号不同步)
- P1-27(executeEffect 函数 PDD 遗漏)
- 以及其他约 40 个错误

### 根因2:Agent 权限三权分立是"设计型"而非"运行型"

#### 2.1 现象

AGENTS.md 和 skill-permissions.md 定义了完美的三权分立(提案权/校验权/写入权),但实际运行中**单线程 AI 扮演所有角色**,自我提案、自我校验、自我写入。

#### 2.2 三重权限定义源矛盾

| 来源 | 文件 | 定义的权限 |
|------|------|-----------|
| 源 A | AGENTS.md | writer-agent 为唯一写入者 |
| 源 B | skill-permissions.md | writer-agent 为唯一 file-write/obsidian-write 拥有者 |
| 源 C | _agent-configs/*.md | **4 个 Agent 配置声称自己直接写入** |

#### 2.3 Agent 配置直接违反权限矩阵的证据

| Agent | 配置文件声称 | 权限矩阵规定 | 冲突 |
|-------|-------------|-------------|------|
| gdd-lead | "通过 MCP 写入更新后的 GDD"(02-gdd-lead.md:41) | obsidian-write: ❌, file-write: ❌ | **直接违反** |
| tech-lead | "编写代码实现游戏功能"(03-tech-lead.md:33) | file-write: ❌ | **直接违反** |
| doc-engineer | "通过 MCP 更新 PDD 文档"(05-doc-engineer.md:34) | obsidian-write: ❌, file-write: ❌ | **直接违反** |
| memory-keeper | "通过 MCP 读取/写入 memory.md"(07-memory-keeper.md:31) | file-read/write: ❌ | **直接违反** |

#### 2.4 writer-agent 缺失问题

- AGENTS.md 定义 8 个 Agent,但 `_agent-configs/` 只有 7 个配置文件
- **writer-agent(唯一写入者)没有配置文件** — 最关键的 Agent 没有任何独立配置

#### 2.5 Agent 调度机制不存在

- skill-permissions.md 定义 `agent-dispatch` 技能,但实际操作中**单个 AI 线程扮演所有角色**
- 无真正的 Agent 分发机制(无 Task 工具调用证据)
- 防幻觉铁律 4"禁止自问自答式验证"被系统性违反

#### 2.6 后果

- 三权分立名存实亡
- AI 自我校验等于无校验
- 92 个未注册 ID、11 处 schema 不一致等错误全部漏过

#### 2.7 影响的错误

- P0-01(MAT-003/MAT-004 名称冲突未被发现)
- P0-02(P-002/P-003 职业归属冲突未被发现)
- P0-05(cards.csv 使用废弃 ID 未被发现)
- P0-07(equipment_slots.csv 结构错误未被发现)
- P0-08(profession 外键失效未被发现)
- P0-10(loadCSV 幻觉)
- P1-01~P1-14(CSV 列结构不一致 11 处未被发现)
- 以及其他约 25 个错误

### 根因3:规则依赖链断裂(基础设施未维护)

#### 3.1 现象

残留覆盖预审规则(residual-coverage-check.md)依赖 ID-ALIAS.md 和 ID-REFERENCE-GRAPH.md,但这两个文件严重滞后/为空,导致预审机制失效。

#### 3.2 证据

| 文件 | 当前状态 | 应有状态 | 失效影响 |
|------|---------|---------|---------|
| ID-ALIAS.md | 第 19 行:"暂无别名" | 应记录 8 个废弃 C-编号的别名映射 | 检测 3(别名残留检测)完全失效 |
| ID-REFERENCE-GRAPH.md | 只列出 4 个前缀(C-/P-/E-/S-) | 应覆盖 19 个前缀的跨系统引用 | 检测 4(跨系统残留检测)覆盖严重不足 |

#### 3.3 时间线证据

- ID-ALIAS.md 和 ID-REFERENCE-GRAPH.md 创建于 2026-07-06
- ID-REGISTRY 在 2026-07-08/07-09 多次变更(废弃 C-001~C-009,新增大量 ID)
- 但 ID-ALIAS 和 ID-REFERENCE-GRAPH 自创建后**再未更新**

#### 3.4 后果

- 5 类残留检测中的检测 3 和检测 4 完全失效
- 无法检测废弃编号残留(导致 cards.csv 使用废弃 ID)
- 无法检测跨系统引用残留

#### 3.5 影响的错误

- P0-05(cards.csv 使用 6 个废弃 ID)
- P1-24(废弃编号残留引用)
- P1-25(ID-ALIAS 严重滞后)
- P1-26(ID-REFERENCE-GRAPH 严重滞后)
- 以及其他约 8 个错误

### 根因4:规则索引与实际规则文件脱节

#### 4.1 现象

AGENTS.md 声称"规则文件索引(14 条)",但 `.trae/rules/` 实际有 16 个规则文件。索引漏掉了关键规则。

#### 4.2 证据

| AGENTS.md 索引数 | 实际规则文件数 | 缺失索引 |
|----------------|--------------|---------|
| 14 条 | 16 个 | collaboration-protocol.md(声称"高于所有其他规则")<br>csv-data-management.md |

#### 4.3 文件名不一致

- AGENTS.md 索引引用"no-hallucination.md"
- 实际文件名为"防幻觉规则.md"(中文)
- 可能导致 AI 搜索时找不到该文件

#### 4.4 后果

- 最高优先级规则 collaboration-protocol.md 未被索引
- 其"讨论→批准→实施"流程可能被跳过
- 未经批准的修改直接写入,导致 75 个错误累积

#### 4.5 影响的错误

- 间接影响所有 75 个错误(规则未索引→规则未执行→错误累积)

### 根因5:规则与数据结构的同步机制缺失

#### 5.1 现象

ID-REGISTRY.md 定义编号格式为 C-001(带连字符),但 CSV 数据使用 C001(无连字符);ID-REGISTRY 标记 C-001~C-009 废弃,但 cards.csv 仍使用这些编号;_schema.csv 定义的列结构与实际 CSV 不一致。

#### 5.2 证据

| 数据源 | 定义/实际 | 另一数据源 | 定义/实际 | 同步状态 |
|--------|----------|-----------|----------|---------|
| ID-REGISTRY.md:47 | C-{3位序号},示例 C-001 | cards.csv:3 | C001(无连字符) | ❌ 不同步 |
| ID-REGISTRY.md:107-115 | C-001~C-003,C-005~C-009 标记❌已废弃 | cards.csv:3-9 | 仍使用 C001-C007 | ❌ 不同步 |
| _schema.csv:15 | cards.csv 6 列,type 枚举 attack-defend-skill-equip | cards.csv:2 | 7 列(多 tags),type 值 basic-skill-equip | ❌ 不同步 |
| _schema.csv:19 | professions.csv 列 profession_id/mp | professions.csv:2 | 实际列 prof_id/mana | ❌ 不同步 |
| _schema.csv:22 | equipment_slots.csv 列 slot_id/name_zh/slot_type | equipment_slots.csv:2 | 实际列 key/value_zh/value_en | ❌ 不同步 |

#### 5.3 缺失的同步规则

ID-REGISTRY 变更后,应强制同步到:

| 同步目标 | 当前状态 | 缺失规则 |
|----------|----------|---------|
| CSV 数据文件(编号格式、废弃编号清理) | ❌ 未同步 | 无同步规则 |
| ID-ALIAS.md(记录旧编号→新编号映射) | ❌ 为空 | 无同步规则 |
| ID-REFERENCE-GRAPH.md(更新跨系统引用) | ❌ 过时 | 无同步规则 |
| 所有 TDD/PDD 文件(更新 ID 引用) | ❌ 未同步 | 文档关联规则.md 提到但不覆盖 CSV |
| 代码文件(更新硬编码 ID) | ❌ 未同步 | 无同步规则 |

#### 5.4 后果

- 编号格式系统性偏差(C-001 vs C001)直接导致 92 个 ID"未注册"(Grep 匹配不上)
- CSV-schema 不一致(11 处)导致数据完整性无法保证
- 废弃编号不清理导致 cards.csv 使用已废弃数据

#### 5.5 影响的错误

- P0-03(92 个 ID 未注册,部分原因是格式不匹配)
- P0-05(cards.csv 使用废弃 ID)
- P0-06(ID 格式系统性偏差)
- P0-07(equipment_slots.csv 结构错误)
- P0-08(profession 外键失效)
- P1-01~P1-14(CSV 列结构不一致 11 处)
- 以及其他约 15 个错误

## 三、6 阶段写入流程的执行漏洞

### 阶段1:生成(提案者)— 漏洞:提案生成无强制触发

| 规则要求 | 实际漏洞 |
|----------|---------|
| gdd-lead/tech-lead 生成提案,含修改清单+依据 | 无证据表明 CSV 数据变更走了提案流程 |
| id-management.md 要求"注册先于写入" | cards.csv 的 C001-C007 未在 ID-REGISTRY 中以该格式注册 |

### 阶段2:残留覆盖预审(writer-agent)— 漏洞:预审依赖文件为空/过时

| 规则要求 | 实际漏洞 |
|----------|---------|
| 执行 5 类检测,依赖 ID-ALIAS 和 ID-REFERENCE-GRAPH | ID-ALIAS 为空,检测 3 完全失效 |
| 检测 4(跨系统残留)需覆盖所有前缀 | ID-REFERENCE-GRAPH 只覆盖 4/19 前缀 |
| 预审报告格式有定义 | 无证据表明任何预审报告被实际生成 |

### 阶段3:系统校核(verify-lead)— 漏洞:校验者配置与权限矩阵矛盾

| 规则要求 | 实际漏洞 |
|----------|---------|
| verify-lead 校验 ID-REGISTRY 一致性 | verify-lead 配置(04-verify-lead.md)极为简略(67 行) |
| 校验 CSV schema | 未提及 CSV schema 校验、版本号校验等具体校验项 |
| 校验报告持久化 | verify-lead 无 file-write 权限,报告只能输出到对话 |
| 独立校验 | 单线程 AI 无法真正"调用"另一个独立角色 |

### 阶段4:人工确认(用户)— 漏洞:确认节点不透明

| 规则要求 | 实际漏洞 |
|----------|---------|
| 输出提案+预审报告+校验报告给用户 | 无证据表明用户收到完整三份报告 |
| 审批记录留存 | .changelog.md 可能未维护 |
| D-Design/D-Draft/D-Register/D-Write/D-Code 五节点 | 无审批记录留存的强制机制 |

### 阶段5:写入(writer-agent)— 漏洞:writer-agent 无配置,其他 Agent 直接写入

| 规则要求 | 实际漏洞 |
|----------|---------|
| writer-agent 是唯一写入者 | **writer-agent 没有配置文件** |
| 使用 Edit 工具精确修改 | 4 个 Agent 配置声称自己直接写入(违反权限矩阵) |
| 每次 Edit 后立即 Read 验证 | 无证据表明此步骤被执行 |

### 阶段6:事后校验(verify-lead)— 漏洞:无证据表明事后校验曾执行

| 规则要求 | 实际漏洞 |
|----------|---------|
| Read 验证每项修改实际写入 | 如果执行过,不可能漏掉 92 个未注册 ID |
| Grep 全文一致性校验 | 如果执行过,不可能漏掉 11 处 CSV-schema 不一致 |
| 变更日志一致性校验 | 如果执行过,不可能漏掉 cards.csv 使用废弃编号 |

## 四、自动化校验机制缺失清单

### 4.1 csv-data-management.md §5.3 的"建议"陷阱

| 校验项 | 规则状态 | 实际工具 | 缺失影响 |
|--------|----------|----------|----------|
| Schema 一致性 | 建议 | **无** | 11 处 CSV-schema 不一致全部漏过 |
| 外键完整性 | 建议 | **无** | _foreign_keys.csv 存在但无校验工具 |
| 唯一性约束 | 建议 | **无** | 重复 ID 无法自动检测 |
| 枚举合规 | 建议 | **无** | cards.csv 的 type 值不在 schema 枚举中 |
| 范围合规 | 建议 | **无** | 数值越界无法自动检测 |
| 版本一致性 | 建议 | **无** | 6 处版本不同步全部漏过 |

### 4.2 其他缺失的自动化校验

| 应有校验 | 现状 | 缺失后果 |
|----------|------|----------|
| ID-REGISTRY 注册状态校验 | 无自动化工具 | 92 个未注册 ID 漏过 |
| ID 格式规范校验(C-001 vs C001) | 无正则校验工具 | 格式系统性偏差 |
| 废弃编号引用检测 | 无自动化工具 | cards.csv 使用废弃编号 |
| TDD/PDD 覆盖完整性 | 无自动化工具 | 5 个 GDD 系统无 TDD/PDD |
| GDD-CSV 元素数量一致性 | 无自动化工具 | 元素清单与 CSV 行数不匹配 |
| PDD-代码状态机一致性 | 无自动化工具 | 状态机不一致 |
| 接口存在性校验(防 loadCSV 幻觉) | 无自动化工具 | loadCSV 接口幻觉 |
| ID-ALIAS 完整性校验 | 无自动化工具 | 别名表为空 |
| ID-REFERENCE-GRAPH 完整性校验 | 无自动化工具 | 引用图严重过时 |

### 4.3 根因:全部校验依赖 AI 自我执行

- 所有校验都设计为"verify-lead 手动执行 Grep/Read"
- 但防幻觉铁律 4 明确禁止"自问自答式验证"
- 单线程 AI 扮演 verify-lead 时,本质就是自我校验,违反铁律 4
- 没有 CI/CD、没有 Git Hook、没有独立校验脚本
- **结论:校验机制在架构层面就是不可执行的**

## 六、75 个错误的生成模型

```
根因1(无自动化强制)
    → AI 在上下文压力下简化流程 → 跳过 6 阶段写入流程
    → 规则存在但不执行 → 92 个未注册 ID、版本不同步、状态机不一致

根因2(三权分立失效)
    → AI 自我提案+自我校验+自我写入 → 违反铁律 4
    → 校验形同虚设 → schema 不一致、loadCSV 幻觉、废弃编号残留

根因3(依赖链断裂)
    → ID-ALIAS 为空 + ID-REFERENCE-GRAPH 过时
    → 残留预审检测 3/4 失效 → 别名残留、跨系统残留全部漏过

根因4(索引脱节)
    → 最高优先级规则未被索引 → "讨论→批准→实施"流程被跳过
    → 未经批准的修改直接写入 → 75 个错误累积

根因5(同步机制缺失)
    → ID-REGISTRY 变更不传播到 CSV/代码
    → 格式偏差(C-001 vs C001) + 废弃编号不清理
    → 92 个 ID"未注册"(格式不匹配) + 编号定义冲突
```

## 七、关键缺失规则建议

### 7.1 缺失规则清单

| 编号 | 缺失规则 | 优先级 | 解决的根因 |
|------|---------|--------|-----------|

| 缺失2 | 代码-文档同步强制规则 | P0 | 根因1+5 |
| 缺失3 | 版本号管理规则 | P0 | 根因1+5 |
| 缺失4 | 命名规范强制执行规则 | P0 | 根因1+5 |

### 7.2 各缺失规则的详细说明

#### 缺失1:GDD 变更同步规则

- **现状**:GDD-COMBAT-001 标记 C-001~C-009 废弃,但 cards.csv 仍使用 C001-C007
- **应补规则**:GDD/ID-REGISTRY 变更后,必须强制同步到:
  1. 所有 CSV 数据文件(编号格式、废弃编号清理)
  2. ID-ALIAS.md(记录旧编号→新编号映射)
  3. ID-REFERENCE-GRAPH.md(更新跨系统引用)
  4. 所有 TDD/PDD 文件(更新 ID 引用)
  5. 代码文件(更新硬编码 ID)
- **现有覆盖**:文档关联规则.md 提到"变更传播"但仅针对 GDD→TDD→PDD→代码,**未覆盖 CSV 和 ID-ALIAS/ID-REFERENCE-GRAPH**

#### 缺失2:代码-文档同步强制规则

- **现状**:PDD 只有 PDD-COMBAT-001,5 个 GDD 系统无 PDD;状态机不一致
- **应补规则**:
  - 代码变更后必须在 N 分钟内同步 PDD(当前无时间约束)
  - 新建.js/.gd 文件时强制创建对应 PDD
  - PDD 覆盖完整性校验(每个 GDD 系统必须有对应 PDD)

#### 缺失3:版本号管理规则

- **现状**:6 处版本号不同步
- **应补规则**:
  - 版本号递增规则(何时+0.0.1,何时+0.1.0,何时+1.0.0)
  - 版本号同步校验(每次 CSV 结构变更必须同步_schema.csv 版本)
  - GDD 引用版本号与_schema.csv 版本号一致性校验

#### 缺失4:命名规范强制执行规则

- **现状**:C-001 vs C001 格式系统性偏差
- **应补规则**:
  - ID 格式正则校验工具(强制执行 `^[A-Z]+(-[0-9]+)+$` 格式)
  - CSV 写入前 ID 格式校验
  - 代码中 ID 引用格式校验

#### 缺失5:CSV-Schema 一致性校验规则

- **现状**:11 处 CSV 列结构与 schema 不一致;§5.3 标注为"建议"
- **应补规则**:
  - 将 §5.3 从"建议"升级为"强制"
  - 提供校验脚本(读取_schema.csv 定义,校验每个 CSV 的列名、类型、枚举值、范围)
  - CI/CD 或 pre-commit Hook 强制执行

#### 缺失6:TDD/PDD 覆盖完整性规则

- **现状**:5 个 GDD 系统无 TDD/PDD
- **应补规则**:
  - 每个 GDD 系统必须在 N 天内完成对应 TDD
  - 每个 TDD 必须在代码实现后 N 天内完成对应 PDD
  - 覆盖率报告(系统数 vs TDD 数 vs PDD 数)

#### 缺失7:Agent 配置一致性规则

- **现状**:4 个 Agent 配置文件直接违反 skill-permissions.md 权限矩阵
- **应补规则**:
  - Agent 配置文件必须与 skill-permissions.md 权限矩阵一致
  - 配置文件变更必须同步权限矩阵
  - 定期审计配置文件与权限矩阵的一致性
  - 补充 writer-agent 的配置文件

#### 缺失8:自动化校验工具规则

- **现状**:全部校验依赖 AI 手动执行,无任何自动化工具
- **应补规则**:定义必须提供的校验脚本:
  - ID-REGISTRY 注册状态校验脚本
  - ID 格式正则校验脚本
  - CSV-Schema 一致性校验脚本
  - 外键完整性校验脚本
  - 废弃编号引用检测脚本
  - TDD/PDD 覆盖完整性校验脚本
  - 版本号同步校验脚本

#### 缺失9:ID-ALIAS/ID-REFERENCE-GRAPH 维护规则

- **现状**:ID-ALIAS 为空,ID-REFERENCE-GRAPH 严重过时
- **应补规则**:
  - 每次 ID 变更(新增/废弃/重命名)必须同步更新 ID-ALIAS
  - 每次新增前缀或跨系统引用必须同步更新 ID-REFERENCE-GRAPH
  - 定期审计(每周)两个文件的完整性

#### 缺失10:规则索引完整性规则

- **现状**:AGENTS.md 索引 14 条,实际 16 个规则文件
- **应补规则**:
  - AGENTS.md 规则索引必须与 .trae/rules/ 目录完全一致
  - 新增规则文件时必须同步更新 AGENTS.md 索引
  - 规则文件名变更时必须同步更新索引引用

## 十、核心结论

### 10.1 75 个错误的本质

**75 个错误不是 75 个独立错误,而是 5 个系统性根因的 75 种表现形式。**

### 10.2 最关键的一句话

> **项目的规则体系是"设计型"的而非"运行型"的 — 规则定义了完美的流程,但没有自动化机制强制执行这些流程,导致规则在实践中被系统性绕过。**

### 10.3 修复策略

修复 75 个错误不需要 75 个补丁,而是要:

1. **建立自动化校验工具**(最关键)— 让规则从"文档型"变为"执行型"
2. **修复 Agent 配置一致性** — 让三权分立从"设计型"变为"运行型"
3. **建立同步机制** — 让 ID-REGISTRY 变更自动传播到所有依赖文件
4. **维护基础设施** — 补全 ID-ALIAS 和 ID-REFERENCE-GRAPH
5. **同步规则索引** — 确保所有规则都被正确索引和引用
