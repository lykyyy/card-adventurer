# 文档关联规则

## ID 绑定要求
每个 GDD 文档必须有唯一 ID：GDD-{系统}-{序号} 示例：GDD-COMBAT-001, GDD-CARD-002
每个 TDD 文档必须引用其来源 GDD ID TDD ID：TDD-{系统}-{序号}（HTML版与Godot版用文件名后缀区分，如TDD-100-001-html.md / TDD-100-001-godot.md）
每个 PDD 文档必须引用其来源 TDD ID 和 GDD ID PDD ID：PDD-{系统}-{序号}
代码文件头部注释必须标注对应的 PDD ID
变更传播
GDD 变更时，检查所有引用该 GDD ID 的 TDD/PDD
TDD 变更时，检查所有引用该 TDD ID 的 PDD
输出受影响文档清单，等待用户确认
传播链：GDD变更 → TDD更新 → PDD更新 → 代码调整

## ID变更传播强制约束

### 变更传播流程（必须执行）
修改ID-REGISTRY中任一编号定义时，必须执行以下4步：
1. Grep该ID在全项目中的引用（搜索范围：docs/GDD/*.md + docs/TDD/*.md + docs/PDD/*.md + data/csv/*.csv + scripts/**/* + AGENTS.md）
2. 逐文件同步更新（使用Edit工具）
3. 每次同步后Read验证（确认修改已写入磁盘）
4. 记录变更传播链（在变更日志中列出所有同步的文件:行号）

### 完成判定
- 变更传播未完成的修正不得声明"已完成"
- 必须提供Grep全文校验证据（搜索结果行数+文件列表）
- verify-lead审查变更传播完整性

## 跨文件ID引用内部链接约束

### 强制规则
1. 跨GDD文件引用ID时，必须使用Obsidian `[[]]` 内部链接格式
2. 链接格式：`[[ID-REGISTRY|显示文本]]`，指向ID-REGISTRY中央数据库（方向A原则：ID-REGISTRY是唯一权威源）
3. 同一ID在多个文件中的引用通过内部链接建立一一映射关系
4. 修改ID定义时，通过Obsidian反向链接快速定位所有引用位置

### 例外
- 同一文件内的ID引用不需要内部链接
- 数值表中的ID引用保持原格式（避免数值追溯困难）

一致性校验
GDD 中的每个系统，必须有对应的 TDD
TDD 中的每个模块，必须在 PDD 中有记录
PDD 中的每个函数，必须有 TDD 对应的接口定义
断链、缺失的文档/条目标记为「需补充」
三文档读取顺序
开始任何任务前，按此顺序读取文档：

先读 GDD 对应章节（了解设计意图）
再读 TDD 对应章节（了解技术方案）
再读 PDD 对应章节（了解当前实现状态）
最后读代码（了解具体实现）
